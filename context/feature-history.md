- **Room Actor Core** (2026-07-20) — First Phase 2 feature (`context/features/phase2/room-actor/room-actor-core.md`): new `internal/room` package — `RoomActor`, `ParticipantState`, and a `RoomEvent` sum type (`ParticipantJoined`, `TelemetryReceived`, `ParticipantDisconnected`) implemented as a Go interface + marker method rather than a flat tagged struct, since `reconnection/grace-period.md`'s later variants (`ParticipantReconnected`, `ParticipantLeft`) would otherwise force optional fields onto a shared struct. `Run()` ticks every 250ms via a `select` over `inbox`/ticker/`ctx.Done()`, broadcasting a ranked `race_state` snapshot (stable tie-break) as `[]byte` over a `chan<- []byte` — non-blocking send, so a full/slow consumer never stalls the actor. `applyEvent` mutates `r.participants` in place and is directly unit-testable without ever calling `Run()` (no goroutines needed), rejecting stale/duplicate/out-of-order telemetry by `Seq <= LastSeq`. Deliberately does **not** follow this project's Handler/Service/Repository layering (context/coding-standards.md) — that convention is for REST domains with a DB round trip, and this is an in-memory actor with none of that shape. The `race_state` JSON struct is defined locally in `internal/room` for now, anticipating `websocket/protocol.md` (not yet built) — flagged to reconcile when that feature lands, most likely by having it import `internal/room`'s types. One implementation-time deviation from the loaded plan: `tick` is an incrementing counter (`r.tickCount++`) rather than a wall-clock `UnixMilli()` timestamp, both for more conventional "tick" semantics and to make the broadcast test deterministic. Verified: `go build`/`go vet`/`gofmt -l .`/`go test ./... -race` clean, including 3 concurrency-focused tests (broadcast-on-tick, clean shutdown on context cancel with no goroutine leak, and concurrent senders on `inbox` from 5 goroutines × 50 events each) — re-ran 5x to rule out timing flakiness before considering it done. No WebSocket wiring, registry, reconnection, or finish-detection in scope here — those are separate, later Phase 2 features that depend on this one. Next feature per context/features/phase2/phase-2-plan.md: `room-actor/room-registry.md`.

- **Room Registry** (2026-07-20) — Second Phase 2 feature (`context/features/phase2/room-actor/room-registry.md`): `internal/room` gains `Registry` (`NewRegistry`/`Spawn`/`Get`/`Remove`) matching the spec's data shape exactly — a `sync.RWMutex`-guarded `map[string]*RoomActor`, single-instance-only (Phase 4 replaces this with Redis-backed ownership). Resolved a gap the spec itself left open (flagged during `load`/`start`): `Spawn`'s signature has no `broadcast chan<- []byte` param, but `NewRoomActor` requires one — solved by changing `RoomActor`'s `broadcast` field to a bidirectional `chan []byte` (created internally by `Spawn`) and adding an exported `Broadcast() <-chan []byte` accessor, so the not-yet-built `websocket/ws-endpoint.md` can read outgoing snapshots after a `Get` without `Spawn`'s signature needing to change. Wired the one hook the spec called for that's actually buildable today: `POST /races/{id}/start` now calls `registry.Spawn(...)` after a successful start. This required `RaceHandler` to hold both the `*room.Registry` and the process's **root** `context.Context` (not `r.Context()`) — using the per-request context would have cancelled the room actor the instant the HTTP handler returned, since `net/http` cancels a request's context on return; the root context is threaded from `internal/app.go` through `httpserver.RegisterRoutes` alongside the existing `pool` param. Deliberately put the `Spawn` call in the **handler**, not `RaceService`, despite `RaceService` normally holding orchestration logic — spawning an in-memory actor isn't a repository-backed business operation the way the rest of `RaceService` is, and threading a `*room.Registry` through `NewRaceService` would have forced an unrelated constructor-signature change onto all ~15 existing `RaceService` unit tests for a concern those tests don't exercise; the handler-level hook only touched the 2 actual `NewRaceHandler(...)` call sites. `Remove` was **not** wired into `race-completion/finish-race.md` or `reconnection/grace-period.md` — neither exists yet, exactly as flagged during `load`. Verified: `go build`/`go vet`/`gofmt -l .`/`go test ./... -race` clean, including the two concurrency scenarios the spec explicitly required (concurrent `Get` during `Spawn`, `Remove` racing an in-flight `Get`, both across 50 races) — re-ran the `internal/room` package 3x to rule out timing flakiness. Next feature per context/features/phase2/phase-2-plan.md: whichever of `websocket/ws-endpoint.md`, `race-completion/finish-race.md`, or `reconnection/grace-period.md` is next in that plan's ordering.

- **WebSocket Protocol** (2026-07-20) — Third Phase 2 feature (`context/features/phase2/websocket/protocol.md`): new `internal/ws` package (not `internal/websocket`, to avoid a future name clash with whichever WS library `websocket/ws-endpoint.md` adds), pure JSON encode/decode with no Handler/Service/Repository layering — same reasoning as `room-actor-core.md`. Closed the reconciliation gap that feature's history entry flagged: `internal/room`'s private `raceStateMessage`/`participantSnapshot` structs are now exported in place as `RaceStateMessage`/`ParticipantStateJSON` (rename only, no behavior change), so `internal/ws` reuses them instead of redeclaring an identical shape — keeps the dependency one-directional (`ws` → `room`; `room` doesn't need to know about `ws`). Resolved the design question flagged during `load`/`start`: since the wire schema's `join_race` message only carries `race_id` but `room.ParticipantJoined` also needs `DisplayName`, `decodeClientMessage([]byte) (ClientMessage, error)` only parses/validates the envelope (known `type`, valid JSON) as literally specified, and a separate unexported method, `ClientMessage.toRoomEvent(userID, displayName string) (room.RoomEvent, error)`, does the `type`-dispatch into `RoomEvent` variants — taking identity as caller-supplied params since the future `ws-endpoint.md` will already have them from the verified session token. Also deliberately did **not** add an `encodeRaceStateMessage` despite the spec listing "one function per outbound type": `RoomActor.broadcastSnapshot` (from `room-actor-core.md`) already marshals and hands out pre-encoded `race_state` bytes over `Broadcast()`, so a second encoder for the same JSON shape would be unused dead code today — only `encodeRaceFinishedMessage` was added, since `RaceFinishedMessage`/`RaceResultJSON` don't exist anywhere yet (`race-completion/finish-race.md` isn't built). Tests live in `package ws` (not `ws_test`), matching `internal/room`'s established convention for same-package testing of unexported pure-logic functions. Verified: `go build`/`go vet`/`gofmt -l .`/`go test ./... -race` clean across the whole module, including the new `internal/ws` tests (decode success/failure paths for both message types, both `RoomEvent` conversions, and the finished-message encode round-trip) and confirming the `internal/room` rename didn't break its existing tests. Next feature per context/features/phase2/phase-2-plan.md: `websocket/ws-endpoint.md`.

- **WebSocket Endpoint** (2026-07-20) — Fourth Phase 2 feature (`context/features/phase2/websocket/ws-endpoint.md`): `GET /ws?race_id=...&session_token=...`, added to `internal/ws` (not a new package) alongside the protocol layer. Added `github.com/coder/websocket` as the WS library per explicit request (project-overview.md §11 left either `gorilla/websocket` or `nhooyr.io/websocket` acceptable; `coder/websocket` is `nhooyr.io/websocket`'s renamed continuation) — its context-native `Read`/`Write` fit this project's context-driven goroutine style better than `gorilla/websocket`'s deadline-based cancellation. Resolved every gap flagged during `load`/`start`: (1) **fan-out** — `RoomActor.Broadcast()` is one channel per room, but each connection needs its own buffered channel, so a per-room `hub` (new `hub.go`) fans broadcasts out; refined mid-implementation from the sketched mutex-guarded map to a channel-driven single-writer design instead (documented in the new `docs/concurrency.md`, added this feature per explicit request after a design-rationale discussion) — no mutex on the hot path, only `hubRegistry`'s lazy-create bootstrap needs one; (2) added `RoomActor.Context()` and `RoomActor.Send(ev RoomEvent)` accessors to `internal/room` (`Send` guards against blocking forever post-shutdown via a `select` on `ctx.Done()`, the same reasoning `hub.registerConn`/`unregisterConn` reuse against their own `closed` channel); (3) `displayName` falls back to `userID` (no DB round-trip, honoring the spec's "no new Postgres access" literally); (4) `applyEvent`'s `ParticipantJoined` case now calls `broadcastSnapshot()` immediately, satisfying protocol.md's "immediate snapshot on join" requirement that nothing had implemented yet; (5) the reader goroutine's read-error exit path pushes `room.ParticipantDisconnected` via `Send`, wiring up an event type `room-actor-core.md` had already built but nothing fed yet. `WSHandler.ServeHTTP` runs no Handler/Service/Repository layering (no DB round-trip) and is registered directly as `GET /ws`, deliberately outside `middleware.Auth` since it authenticates via the query-string `session_token`, not the `Authorization` header — reuses `cfg.CORSAllowedOrigin` for `coder/websocket`'s `OriginPatterns`, since without it the frontend's cross-origin handshake would be rejected by default (a gap neither this spec nor the original CORS work had flagged). A `wsConn` interface lets most tests run against a fake connection (`fake_conn_test.go`) instead of real sockets — one real end-to-end suite (`endpoint_integration_test.go`) still dials a real `coder/websocket` client against `httptest.Server` for the happy path and all three rejection cases, proving the wire-level integration actually works. Verified: `go build`/`go vet`/`gofmt -l .`/`go test ./... -race` clean across the whole module (`go mod tidy` after adding the dependency); `internal/ws`/`internal/room` re-run 5x with no flakiness, matching this project's concurrency-feature verification bar. Not yet wired: `reconnection/grace-period.md`'s grace-period timer (the disconnect event is now sent, but nothing times it out yet) and `race-completion/finish-race.md` (no `race_finished` message is ever actually sent). - **Reconnection & Grace Period** (2026-07-21) — Fifth Phase 2 feature (`context/features/phase2/reconnection/grace-period.md`). Two open design decisions were resolved *before* `start` (with the user, across a `load`-time design discussion) and the spec files updated on disk to match, rather than left as in-code judgment calls: **Decision 1** — no distinct `ParticipantReconnected` event/`Writer` field (the spec's original shape); a reconnect reuses `ParticipantJoined`, told apart from a fresh join entirely inside `applyEvent` by checking existing participant state, since per-connection writer channels live in `internal/ws`'s `hub` and were never something `RoomActor` could plug a `Writer` into anyway. **Decision 2** — a reconnect attempt *after* the grace period already expired is actively rejected (not silently allowed to rejoin fresh): `RoomActor` gained its first synchronous query, `IsEvicted(userID) bool` — a request-with-reply-channel placed on the same `inbox` as every other event, answered inside `applyEvent`, which `ws-endpoint.md`'s `ServeHTTP` calls before the WS upgrade and rejects with the same `401` as an invalid token. Implementation: `ParticipantState` gained `DisconnectedCount int` (in-memory only — deferred to `race-completion/finish-race.md`'s eventual transaction, since no batched-write mechanism this spec assumed actually exists in this codebase) and an unexported `graceTimer *time.Timer`; `RoomActor` gained an `evicted map[string]struct{}` and a package-level `var gracePeriodDuration = 30 * time.Second` (var, not const, so tests can shorten it — `withShortGracePeriod` test helper). The single new `RoomEvent` variant is `ParticipantLeft` (self-scheduled by the room actor via `time.AfterFunc` calling its own `Send`), guarded in `applyEvent` against a genuine race between an already-fired timer and an in-flight reconnect landing at nearly the same moment — only honored if the participant is still marked disconnected at apply time, caught and tested (`TestRoomActor_ApplyEvent_ParticipantLeft_StaleEventIgnoredAfterReconnect`) before it ever shipped. Also resolved a second cross-spec ambiguity found while reading `room-registry.md` again during `load`: that spec attributes empty-room teardown to this feature, but the actual mechanism (Postgres write, `race_finished` broadcast, actor/registry teardown) is `race-completion/finish-race.md`'s "zero participants remaining active" finish condition — `grace-period.md` and `finish-race.md` were both updated on disk to make that split explicit; this feature's own responsibility ends at removing the participant and marking them evicted. **Bug caught after initial implementation, before `complete`**: the first cut of `applyEvent`'s `ParticipantJoined` branch only preserved existing state when `DisconnectedAt != nil`, so a *duplicate* `join_race` from a still-connected participant (e.g. two tabs, a client retry) fell into the "unknown participant" branch and silently reset `WordsCorrect`/`LastSeq`/`DisconnectedCount` to zero mid-race — caught by directly reasoning through the condition when asked about it, not by a failing test (no test covered that path yet); fixed by widening the reuse condition to any already-known participant and narrowing the `DisconnectedAt != nil` check to only gate the reconnect-specific timer/flag cleanup, with a regression test (`TestRoomActor_ApplyEvent_ParticipantJoined_DuplicateWhileConnected_PreservesProgress`) added and confirmed to fail against the pre-fix code. Verified: `go build`/`go vet`/`gofmt -l .`/`go test ./... -race` clean across the whole module, `internal/room`+`internal/ws` re-run 5x with no flakiness; `internal/room` gained 10 new tests (disconnect timer/count, reconnect preserves progress, duplicate-join-while-connected, `ParticipantLeft` remove+evict, the stale-event race guard, unknown-participant no-ops, the eviction query, plus two goroutine-based real-timer tests) and `internal/ws` gained one integration test that simulates eviction via directly `Send`-ing the exported `ParticipantLeft`/`ParticipantDisconnected` events (no need to wait a real 30s) and confirms the WS handshake is rejected. Explicitly out of scope, deferred by user request to a separate future change: making `POST /races/{id}/join` idempotent for an already-joined participant while a race is still `pending` (currently returns `409 already_joined`) — unrelated to this feature's package (`internal/race`, not `internal/room`/`internal/ws`), to be scoped separately. Next feature per context/features/phase2/phase-2-plan.md: `race-completion/finish-race.md`.

- **Race Completion** (2026-07-21) — Sixth and final backend Phase 2 feature (`context/features/phase2/race-completion/finish-race.md`). The spec's `func (s *RaceService) FinishRace(...)` sketch didn't account for a real blocker, found by checking the actual dependency graph rather than the spec's code sample: `internal/race` already imports `internal/room` (`RaceHandler` holds `*room.Registry`), so a room actor calling `RaceService` directly would be `room → race` stacked on the existing `race → room` — a genuine import cycle. Resolved the same way this project already resolves Repository interfaces (coding-standards.md: "interfaces live next to their consumer"): `RaceFinisher` and its `ParticipantResult` data shape now live in `internal/room`, satisfied structurally by `RaceService.FinishRace` — no new import direction needed. - **Fix Spurious InboundKindDisconnected on Race Finish** (2026-07-27) — Found via interactive manual play-testing right after `multi-instance-dev-setup-verification` landed (watching `nats sub "room.>"` while playing a solo race): finishing a race always published an `InboundKindDisconnected` envelope for every participant, even on a completely normal, expected finish with nobody actually dropping.
