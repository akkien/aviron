- **Reconnection & Grace Period** (2026-07-21) — Fifth Phase 2 feature (`context/features/phase2/reconnection/grace-period.md`). Two open design decisions were resolved *before* `start` (with the user, across a `load`-time design discussion) and the spec files updated on disk to match, rather than left as in-code judgment calls: **Decision 1** — no distinct `ParticipantReconnected` event/`Writer` field (the spec's original shape); a reconnect reuses `ParticipantJoined`, told apart from a fresh join entirely inside `applyEvent` by checking existing participant state, since per-connection writer channels live in `internal/ws`'s `hub` and were never something `RoomActor` could plug a `Writer` into anyway. **Decision 2** — a reconnect attempt *after* the grace period already expired is actively rejected (not silently allowed to rejoin fresh): `RoomActor` gained its first synchronous query, `IsEvicted(userID) bool` — a request-with-reply-channel placed on the same `inbox` as every other event, answered inside `applyEvent`, which `ws-endpoint.md`'s `ServeHTTP` calls before the WS upgrade and rejects with the same `401` as an invalid token. Implementation: `ParticipantState` gained `DisconnectedCount int` (in-memory only — deferred to `race-completion/finish-race.md`'s eventual transaction, since no batched-write mechanism this spec assumed actually exists in this codebase) and an unexported `graceTimer *time.Timer`; `RoomActor` gained an `evicted map[string]struct{}` and a package-level `var gracePeriodDuration = 30 * time.Second` (var, not const, so tests can shorten it — `withShortGracePeriod` test helper). The single new `RoomEvent` variant is `ParticipantLeft` (self-scheduled by the room actor via `time.AfterFunc` calling its own `Send`), guarded in `applyEvent` against a genuine race between an already-fired timer and an in-flight reconnect landing at nearly the same moment — only honored if the participant is still marked disconnected at apply time, caught and tested (`TestRoomActor_ApplyEvent_ParticipantLeft_StaleEventIgnoredAfterReconnect`) before it ever shipped. Also resolved a second cross-spec ambiguity found while reading `room-registry.md` again during `load`: that spec attributes empty-room teardown to this feature, but the actual mechanism (Postgres write, `race_finished` broadcast, actor/registry teardown) is `race-completion/finish-race.md`'s "zero participants remaining active" finish condition — `grace-period.md` and `finish-race.md` were both updated on disk to make that split explicit; this feature's own responsibility ends at removing the participant and marking them evicted. **Bug caught after initial implementation, before `complete`**: the first cut of `applyEvent`'s `ParticipantJoined` branch only preserved existing state when `DisconnectedAt != nil`, so a *duplicate* `join_race` from a still-connected participant (e.g. two tabs, a client retry) fell into the "unknown participant" branch and silently reset `WordsCorrect`/`LastSeq`/`DisconnectedCount` to zero mid-race — caught by directly reasoning through the condition when asked about it, not by a failing test (no test covered that path yet); fixed by widening the reuse condition to any already-known participant and narrowing the `DisconnectedAt != nil` check to only gate the reconnect-specific timer/flag cleanup, with a regression test (`TestRoomActor_ApplyEvent_ParticipantJoined_DuplicateWhileConnected_PreservesProgress`) added and confirmed to fail against the pre-fix code. Verified: `go build`/`go vet`/`gofmt -l .`/`go test ./... -race` clean across the whole module, `internal/room`+`internal/ws` re-run 5x with no flakiness; `internal/room` gained 10 new tests (disconnect timer/count, reconnect preserves progress, duplicate-join-while-connected, `ParticipantLeft` remove+evict, the stale-event race guard, unknown-participant no-ops, the eviction query, plus two goroutine-based real-timer tests) and `internal/ws` gained one integration test that simulates eviction via directly `Send`-ing the exported `ParticipantLeft`/`ParticipantDisconnected` events (no need to wait a real 30s) and confirms the WS handshake is rejected. Explicitly out of scope, deferred by user request to a separate future change: making `POST /races/{id}/join` idempotent for an already-joined participant while a race is still `pending` (currently returns `409 already_joined`) — unrelated to this feature's package (`internal/race`, not `internal/room`/`internal/ws`), to be scoped separately. Next feature per context/features/phase2/phase-2-plan.md: `race-completion/finish-race.md`.
- **Race Completion** (2026-07-21) — Sixth and final backend Phase 2 feature (`context/features/phase2/race-completion/finish-race.md`). The spec's `func (s *RaceService) FinishRace(...)` sketch didn't account for a real blocker, found by checking the actual dependency graph rather than the spec's code sample: `internal/race` already imports `internal/room` (`RaceHandler` holds `*room.Registry`), so a room actor calling `RaceService` directly would be `room → race` stacked on the existing `race → room` — a genuine import cycle. Resolved the same way this project already resolves Repository interfaces (coding-standards.md: "interfaces live next to their consumer"): `RaceFinisher` and its `ParticipantResult` data shape now live in `internal/room`, satisfied structurally by `RaceService.FinishRace` — no new import direction needed. Wiring stayed minimal: rather than reordering `app.go`/`route.go` (checked directly — `room.NewRegistry()` is constructed there *before* `RaceService` exists), `Registry.Spawn`/`NewRoomActor` just grew one `finisher` parameter, and `RaceHandler.Start`'s existing `registry.Spawn(...)` call passes its own `h.svc`.
